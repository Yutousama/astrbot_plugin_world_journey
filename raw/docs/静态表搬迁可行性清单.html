01先把反馈核实一遍

DonahueMa 的原话是这样的：

「旅行的饮食安排好像有点太单一了，比如重启 ['重庆小面', '毛血旺', '酸辣粉']，最标志性的火锅和串串啥的没有， 我喊鱼自己去吃了 3 天她也没去，连续吃了两天串串。如果不想增加池子的可选数量，那么建议可以不把池子定死， 留一些她自行选择的机会。」

我按他说的城市查了代码，两句都成立，而且比他说得更严重：

项目实测
重庆美食池['重庆小面', '毛血旺', '酸辣粉']，3 样，确实没有火锅和串串
同一座城的标签表FEATURES.chongqing.food = '火锅' —— 两个表自己打架
成都美食池也是 3 样，也没有火锅；标签同样写着「火锅」
全量分布185 城全覆盖，中位 3 样，最少 3、最多 8，133 座城 ≤3 样

也就是说这不是「漏了重庆」，是整张表的密度本来就只有三行。 先前已经打过两轮补丁：不够三样就从大区菜补、再不够从国家菜补、 「Mr.Q 说每城要 10 种」于是硬凑到 12 样 —— 补池表本身又加了 7.7 KB。 补丁叠到第三层，说明这条路已经到极限了。

他提的第二件事，跟池子无关

「我喊鱼自己去吃了 3 天她也没去」—— 这不是池子大小的问题。 改日程的工具有两个，journey_set_slot（改某一格）和 journey_plan_change（改景点）， 都能用，我 11-13 还给 set_slot 补了「凌晨无格可改时新增一格」。 她没去，是她没调工具 —— 那属于提示词和工具描述的说服力问题，靠扩充池子永远修不好。

所以反馈里其实是两件事：① 池子窄（数据问题）② 她不听指令（提示词问题）。 报告下面只解决 ①。② 单独立一项，别混在一起改，否则改完池子她照样不去。

02先纠一个账：什么进上下文，什么不进

你说「文件大小和上下文都会少很多」。文件大小对，上下文不对。 这个区分很重要，因为它决定了该不该为「省上下文」去重构。

cities.ts 是代码。她读不到代码，只有工具回执和提示词会进上下文。 我实测了三条回执： 

journey_now     107 字   「重庆。在家，随时可以动身。家里这样：潮……」
journey_stats    90 字
envPromptVars   9 个变量，1.8 KB

没有一条夹带景点清单或菜名列表。真正每回合固定出现在上下文里的是这些：

内容体积什么时候进上下文能不能省
21 个工具的 schema23.3 KB每回合 能，但精简描述会掉准确率
ENV_PROMPT.md17.3 KB每回合能，但要逐条核「删了会不会让她犯错」
提示词变量（9 个）1.8 KB每回合不能，都是当前状态
cities.ts 里的 11 张静态表200.2 KB从不 省的是包体积和维护成本，不是上下文

口径说明：上面三行全部按 UTF-8 字节数，不是字符数（中文一字三字节，两者差得远）。 工具那行是紧凑 JSON 实测 23 910 字节；美化版（带缩进）是 27 521 字符，那个形状不会真的进上下文，别拿它算。 工具的 description 本身已经是英文（面向模型写的），能压的主要是参数说明那 9.6 KB。 不同端口对 token 的折算不一样，这里不换算成 token。

03「让 coop 自己调大模型」有三条路，只有两条走得通

我把三条路都查到底了。结论先说：宿主留了一个「另起一次模型调用」的接口，但当前版本没有接上， 所以最省那条捷径现在不能用。

路线谁付账准确度现在能用吗
A. 让她自己说
把「从池子里挑」改成「按约束报一个」		 零额外调用模型常识级：知道重庆有火锅串串，不知道哪家店还开着 能，今天就能改
B. 扩展自己调一次模型
host.cognition.request()		 走已有端点计费和 A 差不多，还多一次延迟 不能用
C. 查真实世界
高德 place/text		 你的 key，有日配额真实：店名、地址、类型都是真的 能用，已有样板

为什么 B 走不通

一句话：不是难做，是那条线在宿主里根本没接上。 宿主确实留了一个「另外再问一次模型」的插口，但插口后面是空的 —— 当前人格层（cormini，就是「可缇mini」）没有实现这个能力。 扩展里写 host.cognition.request(...)，拿到的是 undefined，第一行就崩。 不是配置错、不是 key 没填、也不是我们调用姿势不对。

一、先把 B 想干的事翻译成人话

三条路的区别只有一条：她这次思考，是一次还是两次。

  • A（让她自己说）：她本来就要想一次「今天干嘛」，顺手说了「吃火锅」。 不额外调用，不额外等待。
  • B（扩展另起一次调用）：她说完，扩展再单独发一个请求给模型： 「重庆这个点有什么该吃的？」再买一次调用。
  • C（查高德）：不问模型，直接查外部库，拿真店名。

A 和 B 的知识面完全一样 —— 都是「模型知道重庆有火锅，不知道哪家店今天还开着」。 差别只在钱和延迟。所以 B 要多花的钱，买的不是「更准」，是「隔离」：在她主对话之外再开一次口。

二、断在哪一步

[1] 扩展发起申请    host.cognition.request()
         |
         v
[2] 宿主检查        makeCognition()   <-- 先看人格层有没有实现
         |
         v
[3] 人格层 cormini  persona.cognition  <-- 这一项不存在
         |
         v
    取到空值，直接返回 undefined

宿主那边的代码只有三行（core/core.ts:378）：

const impl = this.persona.cognition;
if (!impl) return undefined;   // 没人接，把电话收回去
// 后面还有三十几行校验、并发计数、异常转换 —— 一行都执行不到

this.persona 就是正在跑的那套人格。它的定义里有记忆（memoryName: 'GitMem'）、 有工具、有提示词，没有 cognition 这一项。于是第二行永远命中。

三、怎么确认「真没有」，而不是「我没找到」

层面查了什么结果
接口定义整个 resources/app（连打包产物 dist）搜 PersonaCognition 只命中 core/types.ts 一处 —— 那是「电话的形状」，不是「电话」
人格实现bots/ 下所有文件搜 cognition 只命中两句界面文案（「元认知笔记」标签），跟这功能无关；cormini 定义里确实没这个字段
我们自己的代码扩展 src/ 搜 cognition / reportUsage 零命中 —— 说明它从未可用过，不是「以前能用后来坏了」

换个说法：宿主把这个能力设计好了、接口写好了、连「请求只能点名自己的工具」这种越权校验都写了， 就差最后一步接线。而接线是人格层的事，不是扩展能补的。

四、「自己带 key 直接调一个模型」为什么也不推荐

这条技术上能写，而且宿主明显预留了位置 —— reportUsage 的注释写着 「Core 不管理 World 自有模型的运行时」，意思就是「你可以自己调，把用量报给我记账就行」。 但代价对不上收益：

代价具体是什么
第二份账单多一套 key、多一处计费口径
多一层缓存不想阻塞她说话，就得后台预生成 + 缓存失效，等于又多一个定时任务
维护翻倍扩展里多一套提示词、一套模型配置、一套重试
换不来 A 拿不到的东西 那个脑子并不比现在这个脑子多知道什么

最后一条是致命的。B 花钱买的是「另开一个脑子的机会」，但那个脑子照样不知道「哪家火锅店今天还开着」 —— 知道这件事的只有 C。所以 B 被 A 和 C 夹在中间：比 A 贵，比 C 假。

还有一个更隐蔽的坑：模型对「重庆有啥吃的」的回答，一年四季都不会变。 你真把它缓存下来，缓存内容本身就会变成一张新的写死的表 —— 问题原地复活，只是从 cities.ts 搬到了缓存里。

五、B 什么时候才真的值得

只有一种场景：你要的是跟她主对话隔离的一段文字 —— 比如让她在后台给自己写内心独白、写日记， 这段字不能污染主上下文。A 做不到（A 只能在她那一回合里说），C 也做不到（C 是查库不是写字）。

那种场景是内容生成问题，不是数据来源问题。真到那天，得先请上游把 PersonaCognition 接上 —— 那是宿主作者的活。Coopani 是打包好的 exe，我们改宿主等于本地分叉，下次升级就丢 （跟 #659 那个 amapKey 明文一个道理：能绕就绕，不碰宿主）。

六、顺带纠正一个容易混的点

B 和「让模型帮忙」不是一回事 —— A 也是让模型帮忙。 A 免费，是因为它搭在她本来就要花的那一次调用上；B 收费，是因为它要多买一次。

C 我实调了一次，能查到真东西

用你配置里那个高德 key，查「重庆 火锅」：

查景点同样是干净的：洪崖洞民俗风貌区 / 风景名胜;风景名胜;风景名胜。 而且这套范式你已经有了 —— geo/hotels.ts 就是走 place/text 查真酒店名、 按城市缓存 7 天、查不到就退回泛称。搬餐饮和景点，是照抄一个跑通的模块，不是新造架构。

06我的建议：三步，先做最便宜的那一步

第一步（半天量级）：美食和夜景交给 A 已做

这两项性质都是「判断」，风险最低，收益最直接 —— 反馈就是冲着它们来的。 池子从「清单」改成「约束 + 三五样打板」，她报什么都行，只要符合「当地、这个点、不是硬菜当早饭」。 先把反馈那一条彻底解决，再看别的。 实际落地的做法见 07 —— 比原计划保守一档，理由也写在那边。

第二步：景色描写也交给 A 未做

理由不是省体积，是质量：静态描写表写不出「此刻下着小雨、六点半、灯刚亮」。 而且 minimal 模式已经证明过「少写反而对」，这一步风险比看起来小。 这一项跟这次的反馈无关，单独拎出来做，别和美食混着改。

第三步：店名走 C 已做

只在「特意去吃 / 打卡」这个场景查一次，其余时候她只说菜名。 照 hotels.ts 抄：按城市 + 想吃什么缓存 7 天、查不到退回泛称、失败绝不影响旅行。

我不建议动的两项：节庆和景点主表。 它们都是「事实」，而且错了最容易被戳穿 —— 编一场不存在的庙会，用户一搜就穿帮； 景点还牵着路线连通，换来源就得重新做避绕路的规划。省 100 KB 不值得冒这个险。

07已经做完了什么

A 和 C 都落地了，代码已进工作区（版本号按惯例等你说「发」再定）。有一条要先说清楚： 我没有删掉那张美食表，而是把它从「定论」降成「起手」。理由在下面第一条，那不是偷懒。

做了什么改在哪解决的是什么
招牌菜先入池 src/plan/dayplan.ts 的 pickFood() 「标签写着火锅，菜表里没有火锅」—— 重庆、成都等 31 座城的自相矛盾
吃什么那一节提示词 ENV_PROMPT.md 新增「吃什么：菜是起手，不是定论」 她可以报菜表以外的东西；连着两顿不许一样；早上不吃火锅

为什么不删那张表

原计划写的是「删掉整张池子」。动手时发现删不动，有三个实际牵连：

  • 照片要菜名。journey_photo 的 dish 参数直接进生图提示词 —— 不给她菜名，照片就只剩「一碗饭」，标题也跟着变空。
  • 12 样补池是给「一座城待十天」用的。删掉表，拉萨、天津这种城只剩三四样， 六十天里会翻来覆去 —— 而那正是 2026-11-08 那四版代码在解决的事。
  • 表是 fallback，不是主语义。这正是项目第 26 条： 弱模型说不出菜名时得有兜底，但兜底不该变成规定动作。

所以改成：表给起手词，她说她想吃的。她说得出就用她的，说不出就用表里的 —— 两条都不丢，反馈那一条也解决了。

31 座城，不是 1 座

这条值得单独说，因为原文只觉得是「重庆漏了火锅」。实测：把标签菜入池那段关掉再跑一遍， 31 座城的招牌菜吃不到 —— 天水麻辣烫、北京烤鸭、太原刀削面、南京鸭血粉丝、洛阳水席、 广州早茶、桂林米粉…… 全都在「标签说有、池里没有」。

这不是漏了一座城，是两张表从来没对齐过。标签是逐城人工填的，菜表是另一批数据， 两边各写各的。修法只能从标签往菜表补 —— 反着补要动 613 行。

还差什么

  • 夜景和景色描写（第二步）还没做 —— 那两项跟这次反馈无关，应该单独一轮， 混在一起改就没法判断是哪一处起的作用。

11仓库是「推」上去的，不是 clone 出来的

这一步本来以为十分钟的事，实际卡了两次，两次都不是小问题。

第一次：git push 挂了 8 分 28 秒，零输出

推送命令发出去之后没有任何反应 —— 不是报错，是一个字都不吐。等了 8 分半手动停掉， 开始怀疑是凭证或者分支名的问题，结果都不是：是这台机器到 github.com 的路太慢。

测的地址单请求耗时说明
https://github.com（主站）12 秒 能通，不是墙。慢到不能用
https://api.github.com3 秒 同一台机器，同一个代理，快四倍

git push 不是一次 HTTP 请求，是十来次往返协商：查 ref、谈能力、传 pack、 等确认。单次 12 秒乘上去，8 分钟不够走完一轮。而 API 是「一问一答」，每次 3 秒， 请求数多但每次都是终局。

判据：「命令没输出」不等于「卡在认证」。先量一下目标域名的单请求耗时 —— 能通但慢到十几秒的，任何需要多次往返的 git 操作都别指望。

改走 Git Data API：158 个文件，35 秒

这条路是四步，本质是「手工拼一个 commit」：

  1. POST /git/blobs —— 一个文件一个，拿回每份内容的 sha
  2. POST /git/trees —— 把「路径 → 文件 sha」列成一张树，拿回树 sha
  3. POST /git/commits —— 挂上树和父提交，拿回提交 sha
  4. PATCH /git/refs/heads/main —— 把分支指向这个提交

第二个坑：差点凭一个样本判「推对了」

第一版是用工作区里的文件直接上传的。传完挑四个文件比 sha，README.md 对得上， 另外三个全不对 —— 当时第一反应是「上传过程损坏了」。

实际原因是行尾：工作区是 CRLF，git 对象里存的是 LF。而 README.md 恰好没有换行结构，所以只有它看起来是对的。如果只挑了它一个来验，这件事就漏过去了。

正确做法不是改文件、也不是重传，而是用 git cat-file blob 取出 git 里的原始字节去上传 —— 内容相同，sha 自然相同，于是两边可以逐文件对账，而不是「看着差不多」。

校验项结果说明
整棵树的 sha相等 远端 main 的 tree == 本地 public 分支的 tree
逐文件 blob sha158 个全等 含中文路径的 docs/静态表搬迁可行性清单.html
白名单生效无越权 顶层没有 cloud/、data-research/、.workbuddy/、 PROGRESS.md、_状态.md

收尾也绊了一下

切回 master 时被两个文件挡住：tools/.play-inbox.txt 与 docs/reply-659.md。它们在 public 分支上被剔掉了，在 master 上仍然被跟踪，checkout 认为「你要切过去就得覆盖未跟踪文件」， 于是拒绝。

用 -f 切回之后，恢复出来的 .play-inbox.txt 字节数变大了 —— 那是 LF 被转成 CRLF 的正常结果，用 diff --strip-trailing-cr 核过内容一致。 「字节数变了」和「内容变了」是两件事，别混。
