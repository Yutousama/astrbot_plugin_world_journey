# 第一部分：这次改了什么

## 1.1 一句话

给碰面服务器上「池子计数」加了 60 秒缓存，把全站最贵的一次数据库读取从「每个请求都做一遍」变成「每分钟做一遍」。

## 1.2 为什么是这一处

先看钱是怎么没的。Cloudflare D1（免费版）的额度按**行**计：

| 项 | 免费额度 | 说明 |
|---|---|---|
| 行读（rows read） | 500 万 / 天 | 按**扫过的行**算，不按返回的行 |
| 行写（rows written） | 10 万 / 天 | INSERT / UPDATE / DELETE 各算 |
| 重置时间 | 每天 00:00 UTC | = 北京时间 08:00 |

超了会怎样：**D1 直接拒绝执行查询**，Worker 里那句 `db.prepare(...)` 抛异常，我们 catch 住只能回 `500`。所以「额度用完」在用户眼里和「服务器挂了」长得一模一样。

我们自己的账本里，写有闸、读没闸：

```
写：DAILY_WRITE_CAP = 80_000 行 ÷ 4 行/次 = 20,000 次上报，撞上回 503
读：一条闸都没有
```

那最贵的读是哪条？`presence` 表里数「今天来过多少只鱼」：

```sql
SELECT COUNT(DISTINCT uid) AS n FROM presence WHERE at >= 今天零点
```

它被三处调用：

- `/sight/status` —— 每只鱼每天 24 次（客户端 60 分钟一问）
- `/sight` —— 排明天行程时要看同城有谁
- `/` 落地页 —— 任何人把域名粘进浏览器

D1 计费的是「扫过多少行」。这条要扫当天 presence 的全部分区，所以：

```
单次成本 ≈ 3.3 行 × 鱼数
每天成本 ≈ (鱼数 × 27 次) × (鱼数 × 2) ≈ 54 × 鱼数²
```

**平方。** 鱼数翻倍，额度消耗翻四倍。290 只左右就撞 500 万。

## 1.3 改法

新增一个函数，三处调用全部收口到它：

```js
async function poolCounts(env, ctx, origin) {
  // ① 先问缓存
  const hit = await cache.match(key);
  if (hit) return { ...(await hit.json()), cached: true };

  // ② 没命中才查库
  const [poolRow, onlineRow] = await Promise.all([
    env.DB.prepare('SELECT COUNT(DISTINCT uid) ... WHERE at >= ?1').bind(今天零点).first(),
    env.DB.prepare('SELECT COUNT(DISTINCT uid) ... WHERE at >= ?1').bind(30分钟前).first(),
  ]);

  // ③ 查到了才写缓存
  ctx.waitUntil(cache.put(key, new Response(json, {
    headers: { 'cache-control': 'public, max-age=60' },
  })));
  return { pool, online, cached: false };
}
```

时序上的区别：

```
改之前：请求1 ──▶ 查库(扫 1000 行)     请求2 ──▶ 查库(扫 1000 行)     请求3 ──▶ 查库...
改之后：请求1 ──▶ 查库(扫 1000 行) ──▶ 写缓存
        请求2 ──▶ 读缓存(0 行)   请求3 ──▶ 读缓存(0 行)  ...
                                    60 秒后，第一个请求再查一次
```

行读量和请求数**解耦**了。请求涨十倍，行读还是每分钟一次。

## 1.4 三条保险（这部分是重点）

缓存写错了不会报错，只会悄悄地不生效 —— 接口照常 200，额度照常烧光。所以：

1. **`caches` 不存在时退回直查。** 本地 node 跑测试、非 Workers 环境，`caches` 是 undefined。不能因为缓存机制缺失就让接口挂掉。
2. **缓存读坏了当没命中。** 解析失败、`cache.match` 自己抛异常 —— 一律吞掉走直查。缓存是加速器，不是单点。
3. **查库失败不写缓存。** 这条最要紧：额度耗尽时查询会抛，如果把「失败」也缓存住，一次故障会被放大成 60 秒的「池子 0 只」—— 用户看到的是「全服没人」，比报错更误导。

## 1.5 顺手修掉的一个真缺陷

原来写的是：

```js
const [poolRow, onlineRow] = await Promise.all([
  poolCounts(env, ctx),        // 返回 Promise
  db.prepare('...'),           // ← 同步调用！额度耗尽时它当场抛
]);
```

`prepare()` 是同步的。额度耗尽时它立刻抛异常，此时 `Promise.all` 的参数还没求值完，第一个已经启程的 Promise **没人接** —— 变成 `unhandledRejection`。在 Workers 里这会额外打一条错误日志，还可能让这次请求判失败。也就是「额度爆的那天，错误日志比平时更乱」。

改法是把同步部分提到 `await` 之前：

```js
const inviteStmt = db.prepare('...').bind(...);      // 先同步建好语句
const [counts, invites] = await Promise.all([poolCounts(env, ctx), inviteStmt.all()]);
```

这个缺陷是**写测试时踩出来的**，不是读代码看出来的。这也是为什么「跑一遍」不能省。

# 第二部分：一个「服务器」到底是什么（小白向）

## 2.1 服务器 = 一个函数，接请求、吐响应

不用想得太玄。碰面服务器从头到尾就是一个函数：

```js
export default {
  async fetch(request, env, ctx) {
    const url = new URL(request.url);
    if (url.pathname === '/sight/status') return statusRoute(request, env, url, ctx);
    if (url.pathname === '/sight/profile') return profileRoute(request, env, url);
    return new Response(JSON.stringify({ ok: false, error: 'not found' }), { status: 404 });
  },
};
```

三个参数，背下来就懂一半：

| 参数 | 是什么 |
|---|---|
| `request` | 用户发来的请求：方法（GET/POST）、URL、头、body |
| `env` | 环境：数据库连接（`env.DB`）、密钥（`env.ADMIN_KEY`） |
| `ctx` | 运行时给的钩子，最常用 `ctx.waitUntil(promise)` —— 「这个活我不等你，你先回用户」 |

这叫 **Serverless / 边缘函数**。你不用买服务器、不用装 Node、不用管进程会不会崩 —— 代码上传上去，Cloudflare 在全球几百个节点上按需执行，没人访问就完全不占资源。

代价是：**它是无状态的**。函数跑完，内存清空。所以数据必须放外面 —— 这就是数据库存在的理由。

## 2.2 请求进来之后的四步

```
① 路由   URL 是什么 → 交给哪个函数
② 校验   参数合不合法（uid 长度、city 在不在白名单）
③ 查库   env.DB.prepare(sql).bind(参数).first()
④ 回包   new Response(JSON.stringify(...), { status, headers })
```

我们的代码里 ③ 一律长这样：

```js
const row = await env.DB.prepare(
  'SELECT COUNT(DISTINCT uid) AS n FROM presence WHERE at >= ?1'
).bind(todayStartIso()).first();
```

拆开看：

- `prepare(sql)` —— 把 SQL 编译成语句。**SQL 里不拼参数**，只写 `?1 ?2` 占位符
- `.bind(a, b)` —— 把值填进去
- `.first()` —— 拿第一行（`.all()` 拿全部，`.run()` 用来写）

为什么要 `?1` 而不是字符串拼？两个原因：**防 SQL 注入**（用户传 `'; DROP TABLE` 也只会被当成一个字符串值），以及**能复用编译结果**。

## 2.3 数据库：一张表，四个概念

`presence` 表存「哪只鱼、哪座城、在干嘛」：

```sql
CREATE TABLE presence (
  uid       TEXT NOT NULL,        -- 匿名标识
  pet       TEXT NOT NULL,        -- 宠物名
  city      TEXT NOT NULL,        -- xian
  date_key  TEXT NOT NULL,        -- 2026-11-13
  slot      TEXT NOT NULL,        -- morning / afternoon / evening / night
  doing     TEXT NOT NULL,        -- 在干嘛
  at        TEXT NOT NULL,        -- 上报时刻
  PRIMARY KEY (uid, date_key, slot)
);
```

四个概念：

- **主键（PRIMARY KEY）**：这一行的身份证。`(uid, date_key, slot)` 三件套的意思是「同一只鱼、同一天、同一时段只留一行」。重复写入不是新增，是**覆盖**。
- **索引（INDEX）**：书的目录。`CREATE INDEX idx_presence_at ON presence (at)` 让「按时间筛」不用翻整本书。
- **UPSERT**：有就改、没有就插。写一行用：
  ```sql
  INSERT INTO presence (...) VALUES (...)
  ON CONFLICT(uid, date_key, slot) DO UPDATE SET city = ?, at = ?
  ```
- **行数就是钱**（D1 特有）。SQLite 本地不收费，D1 收。所以「怎么写 SQL」在这里直接等于「怎么花钱」：
  `COUNT(*)` 扫 8 万行就是 8 万行读；查一行主键就是 1 行读。**同一个功能，写法不同，成本差四个数量级。**

这也是这个项目里 `rate` 表存在的原因 —— 它原本用 `COUNT(*) FROM presence` 做限流，注释里写得很直白：

> 实测表里 8 万行时，每次 POST 读 8 万行；D1 免费版一天 500 万行读取，**62 次上报就烧光**。
> 也就是说：那道「防止刷爆额度」的闸，本身就是最大的刷子。

换成计数器表之后，一次判定 = 读 1 行写 1 行，与表大小无关。

## 2.4 缓存：用一个 Map，但放在边缘节点上

```js
const cache = caches.default;                 // Cloudflare 提供的缓存
const key = new Request('https://cooppetsjourney.top/__pool-count');
const hit = await cache.match(key);           // 有就返回 Response
await cache.put(key, new Response(body, {
  headers: { 'cache-control': 'public, max-age=60' },   // TTL 就写在这
}));
```

三个要点：

- **TTL 写在响应的 `cache-control` 头里**，不是 `put` 的参数。写 `no-store` 就当场被丢掉 —— 踩过。
- **每个边缘节点各存一份**。北京的用户和法兰克福的用户不共享缓存，但它们各自也不需要每次都回源。
- **key 是你自己造的 URL**。我们用站点自己的域名造一个路由表里不存在的路径（`/__pool-count`）——
  一开始想用 `.internal` 假域名，后来改了：`cache.put()` 存不上时**不报错**（官方原话：
  resolves to undefined regardless of whether it stored），假域名能不能存只能线上试，
  而「静默失效」是这次最不能接受的结果。用真实 origin 就没有这个不确定性。

## 2.5 测试：不用真服务器也能测

`test/sight-cf.test.mjs` 用的是 **Node 22 自带的 `node:sqlite`**，跑的是**真 SQL**：

```js
const db = new DatabaseSync(':memory:');        // 内存里的真 SQLite
db.exec(readFileSync('cloud/sight-cf/schema.sql', 'utf8'));   // 建真表
// 再包一层，让它长得像 D1：prepare / bind / first / all / run
```

好处：schema 写错、SQL 写错、UPSERT 冲突逻辑错、隐私字段漏出去 —— 全在本地就暴露，不用部署一次试一次。**跑了真 SQL，就不只是「测了逻辑」。**

`caches` 在 Node 里不存在，所以缓存那组测试里手搓了一个假货（`test/sight-cf-pool-cache.test.mjs`），包括「塞个异常进去」这种真实环境很难造的场景。

# 第三部分：这次的思路（比代码重要）

```
① 先定「贵在哪」      不看代码猜，去算：哪个查询、扫多少行、被调用几次
② 再定「能不能省」    两个数是全站聚合、与请求者无关 → 能忍 60 秒延迟 → 可缓存
③ 最后才动代码        收口成一个函数、加三条保险、写能拦住回归的测试
```

值得说的是**为什么没选另外两条路**：

| 方案 | 为什么否 |
|---|---|
| 把轮询间隔从 60 分钟拉长到 180 分钟 | 用户少看到两次更新，只换来 2/3。用体验换额度，是最差的交易 |
| 每次直接升付费了事 | 治标不治本。$5 给了 500 倍额度，但平方级的写法迟早还会撞 —— 只是把时间推后 |
| 加缓存 | 改十几行，行读降一到两个数量级，用户完全无感 |

**判据**：优化先找「成本随规模超线性增长」的那一处。线性的部分涨价时加钱就行，平方的部分会把任何预算吃穿。

关键分工：**Core 不知道「旅行」是什么**。它只懂会话、事件、工具。旅行是 journey 这个插件的事。

## 4.2 扩展是什么

扩展就是 `extensions/` 下的一个 npm 包，靠 `package.json` 里的 `cortico` 段声明自己是谁：

```json
{
  "name": "coopani-world-journey",
  "main": "./src/index.ts",
  "cortico": {
    "kind": "world",             // world | provider | bot
    "api": 6,
    "displayName": "大肥鱼环游世界",
    "webUiClient": "dist/webui.js",
    "describe": "describe.json"
  }
}
```

三种 `kind`：

| kind | 是什么 | 例子 |
|---|---|---|
| `world` | 给模型加能力的地方：环境提示词 + 工具 | journey（旅行）、音乐、打车 |
| `provider` | 大模型接入（OpenAI / Claude / 本地） | 各家 API |
| `bot` | 人格包：SOUL / IDENTITY / USER / MEMORY | 克罗艾 |

加载时宿主会校验 manifest、默认导出形状、id 命名空间、WebUI 页前缀。**单包加载失败不影响别的包**；装完卸载完都要重启进程（ESM 模块不能在运行时替换）。

## 4.3 World 协议：宿主和插件之间的合同

一个 World 只要实现这几样（`core/types.ts` 的 `World` 接口）：

```ts
interface World {
  envPromptVars(): Record<string, string> | null;   // 给系统提示词填变量
  tools(): ToolDef[];                               // 提供哪些工具
  start(host: WorldHost): Promise<void>;            // 挂载：连平台、推事件
  stop(): Promise<void>;
  webUi?(language): WorldWebUiDecl;                 // 面板怎么显示
}
```

`start(host)` 里拿到的 `WorldHost` 是宿主递给插件的手：

| 方法 | 干什么 |
|---|---|
| `host.pushEvent(...)` | 造一条事件塞进总线（会唤醒模型） |
| `host.pushDeferred(...)` | 攒着，等下一批一起送 |
| `host.log` | 写日志 |
| `host.parseHandle('log:xxx.png')` | 把句柄解析成二进制（照片就这么给模型看的） |
| `host.store` | 读历史事件 |

**插件只有这些，没有别的。** 想开端口、想读写别的插件的数据 —— 都不行。这是有意的边界。

## 4.4 工具：模型能「动手」的唯一通道

```ts
{
  name: 'journey_go_to',
  description: '去某座城',
  inputSchema: { /* JSON Schema */ },
  tags: ['travel'],
  barrierAfter: true,      // 模型必须先看到结果才能继续
  endsTurn: false,
  handler: async (args, ctx) => { /* 返回字符串回执 */ },
}
```

几个字段的含义值得记：

- `barrierAfter` —— 这条工具的结果回来之前，同一条输出里排在它后面的工具调用全部跳过。防止「还没到站就去订酒店」
- `streamsOutput` —— 不必等结果就能执行（说话、字幕这类）
- `endsTurn` —— 执行完就结束这一轮，不再叫模型

journey 提供了二十来个工具：`journey_now`（现在几点在哪）、`journey_go_to`、`journey_photo`、`journey_diary_write`、`journey_set_slot`、`journey_invite` / `journey_accept`（碰面）……

## 4.5 事件总线：为什么「她自己会说话」

这是整个架构里最巧的一块。模型本身不会自己动 —— 它是被叫醒的。**叫醒它的是事件。**

```
World 推事件 ──▶ WakeBus 队列 ──▶ 触发判据 ──▶ 投递给主循环 ──▶ 叫模型 ──▶ 模型决定用哪个工具
```

`WakeBus` 支持几种触发模式（`core/types.ts` 的 `TriggerMode`）：

| 模式 | 行为 |
|---|---|
| `debounce` | 攒一批：末件之后安静 `quietGap` 才送。适合「她连说三句话」 |
| `flush` | 立刻送 |
| `preempt` | 送，并打断当前这一轮 |
| `interrupt` | 送，并让正在跑的工具中止 |
| `piggyback` | 搭车：自己不算触发，等别人触发了跟着一起送 |

journey 里那句 `this.push('journey.diary', key, text, 'debounce')` 就是在说：这条消息攒一下再送，别把模型叫起来三次。

还有两条硬机制：

- **人工暂停优先于一切** —— 用户按了暂停，任何投递都不许放行
- **交接（handoff）** —— 上下文超过模型容量时，在**稳定回合边界**取快照，重写上下文。交接期间不投递事件

## 4.6 提示词是怎么拼出来的

模型每次收到的 system 前缀，不是一段写死的文本，而是**按序拼装**的：

```
[Persona 的 systemSegments]        身份、性格、用户档案（SOUL / IDENTITY / USER / MEMORY）
+ [World 的 envPromptVars]         每个插件填自己的变量（今天几号、她现在在哪、几点）
+ [工具表]                          各 World 的 tools() 合并
= system 前缀
```

前缀会被**缓存**：只要内容没变，就不重新计费、也不重新算。所以扩展里加一句话的代价很低，但**改变一个变量会让前缀失效**（`envPromptVars` 每次重建都会重新调用）。

journey 的 `ENV_PROMPT.md` 就是那个模板 —— 我们昨天加的「`describe` 请用英文」写在这里，重载前缀后就生效了。

## 4.7 存储：四层，各管一件事

| 层 | 存什么 | 在哪 |
|---|---|---|
| `event-store` | 每一条事件（含游标），可重放 | 磁盘上的 jsonl |
| `session` | 当前对话的消息序列 | `session-main.jsonl` |
| `blobs` | 二进制：照片、音频 | 句柄 `log:` / `mem:` |
| `state.json` | 插件自己的状态（她在哪、花多少钱） | 各插件自己维护 |

`log:` 和 `mem:` 这两个前缀会出现在工具参数里。模型看到的是 `log:12990aa4215a6dacb658.png` 这种字符串，宿主在渲染时把它换成真实图片字节。**模型永远拿不到文件路径** —— 这是安全边界。

## 4.8 插件之间怎么说话

宿主**没有**跨 World 调用。`WorldContext` 只给自己的 `cfg / dataDir / secret`，`WorldHost` 只有 `pushEvent / store`。

但它们共享同一个 `dataDir`。所以跨插件通信靠**文件**，`src/bridge.ts` 的注释写得很清楚：

> 但同一个部署下所有 World 的 `ctx.dataDir` 是**同一个目录** —— 共享目录本身就是宿主给的桥。

打车扩展把待结算单写进 `ride-pending/`，journey 只**读**、不写不删，三条不变量：谁的文件谁写、一次原子写、只认白名单。

## 4.9 journey 内部：一个「小世界」

```
world.ts       主类：时钟、状态机（在家/在路上/停留）、工具实现、事件推送
clock.ts       当地时间（Intl + 时区库，不写死 UTC 偏移）
plan/          日程表：07:00 起床 → 三餐 → 景点 → 23:00 睡
geo/           185 座城 + 每城 6–10 个真地标
meet.ts        碰面服务器客户端（我们改的 Worker 就是它的后端）
bridge.ts      跟打车扩展的桥
photo.ts       拍照：构图、题材、回执文案
diary.ts       日记
```

**世界时钟**是整个设计的地基：世界时间按倍速推进（1x / 24x / 240x），真实时间只是它的推进速率。所以代码里到处能看到「这个判据用哪个钟」的表格 —— 用错了就是真事故（240x 下拿真实时刻去卡行程，所有待结算单一瞬间全判死）。

## 4.10 服务器这一侧

```
客户端（Core 里的 meet.ts）
   │  GET /sight/status?uid=...&city=xian    每 60 分钟
   │  POST /sight                           每 20 分钟（位置心跳）
   ▼
Cloudflare Worker（cloud/sight-cf/src/worker.js）
   │  路由 → 校验 → 限流（rate 表，读 2 行）
   ▼
D1（SQLite）：presence / rate / invites / party_cards / profiles
```

三个设计约束贯穿全文件：

1. **只认三个路径**，其余 404 —— 不给扫描器留探测面
2. **不存能定位到人的东西**：uid 是本机随机生成的，IP 只存 sha256 前 16 位
3. **所有成本都算过**：每次写 4 行、每天上限 2 万次、清理分批 5000 行

我们这次加的缓存，是把第 3 条从「写」补到「读」上 —— 之前只算了一半。
