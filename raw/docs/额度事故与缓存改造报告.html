01事故：那天到底发生了什么

11 月 12 日下午开始，陆续有用户报「名片点了没反应」「点一次转五秒然后报错」。当时我以为是代码 bug， 查了一整圈没找到 —— 因为代码确实没问题。

真正的线索在本机的客户端日志里。E:\Coopanion\data\logs\core.log 里，所有上报失败的记录时间点排开来是这样的：

  • 11-12 12:28首条「位置没报上去」　零星失败，还不够引起注意
  • 11-12 16:12 起转为密集失败　当天累计 74 条，此后所有请求全挂
  • 11-13 07:57仍在失败　已持续近 16 小时
  • 11-13 08:01:36「位置上报恢复」　自己好了，没有人改过任何东西

08:01 这个时间点就是答案。 D1 的免费额度按官方规定每天 00:00 UTC 重置 —— 换成北京时间正好是 08:00。 恢复发生在重置之后 1 分半，不可能是巧合。

结论修正：这不是 D1 故障，也不是代码 bug，是当天的读取额度在 UTC 08:12（北京 16:12）前后就烧光了， 之后约 16 小时数据库对所有人拒绝查询，Worker 只能回 500。当时我说「链路是通的」没错 —— 我测的时候已经过了零点重置。

02根因：为什么读会比写先崩

先看额度本身

项目免费版每天付费版每月（$5）
行读 rows read500 万250 亿
行写 rows written10 万5000 万
存储5 GB—

写有闸，读没有

代码里对写是设了保护的：DAILY_WRITE_CAP = 2 万次上报（约 8 万行），撞上直接回 503， 还留了 20% 余量给清理任务。这条闸从来没被撞到过 —— 说明写从来不是问题。

而读一条限制都没有。任何客户端、任何时候想读多少读多少。 在一个「必须靠自觉」的维度上，只要有一条查询足够贵，它迟早会把额度吃掉。这是设计层面的漏洞，不是某一行代码写错了。

那条最贵的查询

SELECT COUNT(DISTINCT uid) FROM presence WHERE at >= 今天零点

这条 SQL 只回答一个问题：今天一共来过多少只鱼。它被三处调用 —— /sight/status（每只鱼每天打 24 次）、/sight（排日程时问附近有谁）、落地页（任何人打开域名）。

贵在两件事叠加：

  1. 它是全表扫描。 COUNT(DISTINCT) 要求去重，数据库必须把符合条件的行逐行看一遍才能知道哪些 uid 重复。 索引在这里帮不上忙。
  2. 它按扫过的行计费，不是按返回的行。 扫 100 万行、最后只返回一个数字「500」，计费是 100 万行读。 这是按量计费数据库的通用规则，也是最容易踩的坑。

于是成本变成平方

假设有 N 只鱼，presence 表主键是 (uid, date_key, slot)，每只鱼每天最多 4 行 —— 所以当天全表大约 4N 行。

每只鱼一天打 24 次 status，每次都要扫这 4N 行，于是： 

日行读 ≈ 24N × 4N = 96N²  （实测折算约 60N²，因为不是每只鱼全天在线）

代入免费额度 500 万反解：N ≈ 290 就撞顶。 而昨天实际是 8.2 小时烧完的，反推峰值大约 500 只。 多出来的那部分放大因素，是旧版客户端在失败时不退避、服务器一慢就 60 秒重试一次（就是 11-11 那次 68 只打出 9.8 万请求的同一条毛病）。

注意这是估算，不是实测。60N² 是拿「每鱼每天 24 次、当天 4N 行」推的模型； 真实值受在线时长、落地页访问量、旧版客户端重试行为影响。能确定的只有两件事： 昨天确实烧光了，而且成本确实随用户数平方增长 —— 这一点不看模型也成立，因为「每请求 × 扫全表」本身就意味着请求数和表大小同时涨。

03改法：把那次查询从请求路径上摘下来

思路一句话：这两个数字是全站聚合值，跟「谁在问」无关，所以没必要每次请求都算一遍。

① 缓存没命中
查库 → 扫 4N 行 → 结果写入本机房缓存，存活 60 秒
→
② 缓存命中
60 秒内后续所有请求直接读缓存，零行读
→
③ 60 秒后
缓存过期，下一次请求重新走 ①，再把新的值铺给后面一分钟

于是行读量与请求数解耦：请求涨十倍，行读不变。 实测今天上午同一分钟内连打四次 status，只有第一次查了库。

具体改动

文件改了什么为什么
worker.js 新增 poolCounts()：先查缓存，未命中才查库，结果写入 caches.default，TTL 60 秒 把三处重复的昂贵查询收成一个函数
worker.js reply() 支持自定义响应头；两个接口返回 x-pool-cache: hit | miss 让「缓存到底有没有生效」能用一个 curl 直接量，不用猜
worker.js 把同步的 db.prepare() 提到 Promise.all 之前 修掉一个真实缺陷，见下
测试 新增 sight-cf-pool-cache.test.mjs 5 条用例 数的是「真查库了几次」，不是返回值

顺手修掉的那个缺陷

原来的写法是这样：

const [counts, invites] = await Promise.all([
  poolCounts(env, ctx, url.origin),   // 异步
  db.prepare('SELECT …').bind(…).all() // ← prepare() 是同步的，会当场抛
]);

Promise.all 会先启动第一个，再去执行第二个。 而 prepare() 是同步调用，额度耗尽时它当场抛错 —— 此时第一个 Promise 已经在跑了，却再没有人 await 它的结果， 于是变成一个 unhandledRejection。

说白了：额度爆掉的那天，错误日志会比平时乱得多，因为你同时还会收到一堆「未处理的 Promise 拒绝」。 这会让下次排查更难。改成先把同步部分做完再进 Promise.all，就没有这个窗口了。

这个缺陷是写测试的时候踩出来的，不是读代码看出来的。 我原本只是想验证「失败时不会把 0 写进缓存」，结果那条测试直接把这条报警抖了出来。

04部署：凭据其实一直都在

上一轮我说「本机没有 wrangler 凭据，需要你来跑」，这句话是错的 —— 我只是查错了地方。

真实位置在： 

C:\Users\Administrator\AppData\Roaming\xdg.config\.wrangler\config\default.toml

Windows 上 wrangler 把配置放在 %APPDATA%\xdg.config\.wrangler， 而不是 ~/.wrangler（那是 Linux 和 macOS 的路径）。我 ls ~/.wrangler 看到空的就下了结论 —— 「那里没有」不等于「没有」，这是我在这次任务里犯的判断错误。

撞上的那个巧合

我动手的时刻是 09:33，而文件里记的过期时间是 09:29:25 —— 已经过期 4 分钟。 但文件里还有一个 refresh_token， wrangler whoami 会自动拿它去换一张新的 access token。 所以我既没有重新登录，也没有弹出浏览器授权框，直接把有效期待到了 10:34。

一个必须说清楚的边界

边缘节点的缓存是每个机房各存一份，不是全球共用一份。 所以准确的表述是「同一个机房 60 秒内只查一次库」，而不是「全站 60 秒只查一次」。

整站实际上会是「机房数量 × 每分钟一次」。相比原来「每个请求都扫一遍全天数据」， 这仍然是数量级的下降 —— 但它不是免费的，别当成一个绝对开关。

06还剩什么

事项状态说明
升级付费版等你点Workers & Pages → Plans → Upgrade to Paid，$5/月。我不动你的付款账户
/admin/live 里的同类查询未改管理面板 30 秒一次，也扫全天，量级约占免费额度 6%，但不影响普通用户
本地 admin key 与线上不一致待你确认本地备份那串实测 401；secret 本身存在，应该是后来换过 key、本地没同步
照片页缩略图空白棕块挂起本机复现不了，要用户提供宿主版本 + 页面 + 原图路径
跨零点日程错位未动需要先量清日切逻辑，不是改一行能解决的

为什么建议升级：缓存是「省」，$5 是「够」。现在 pool 112 的量，缓存把行读压到了安全区； 但用户再涨两三倍，免费额度还是会撞。$5 换掉一次为期 16 小时的全站停摆，这笔账不用算。

为什么不改 /admin/live：它只在你打开管理面板时才，不是全站路径； 而且它显示的是「今日累计」这个数，改成 60 秒缓存会让面板上的数字最多晚一分钟 —— 这是改你面板的语义，得你点头。

07.1 数据库与 SQL

术语一句话
跟数据库说话的语言：查、增、改、删都靠它
整库存成一个文件的嵌入式数据库，D1 用的就是它
查。只读不改；贵在内部看过多少行，不在返回几行
增、改、删，统称写，都按受影响行数计费
COUNT / SUM / MAX，把多行压成一个数，几乎总是全表扫
每只宠物的唯一编号，去重和识别都靠它
O(N) 与 O(N²)：量翻倍时，成本翻倍还是翻四倍
